## When to use

- Any list of choices where showing where a click will land helps: menus, nav, segmented controls, result lists.
- Building your own components that should feel like the rest of kinematic.

## When not to use

- **Long virtualized lists.** The highlight measures real elements, so it needs them in the DOM.
- **Static content** that isn't interactive.

## Usage

```tsx
import { HighlightGroup, HighlightItem } from "@/components/ui/fluid-highlight"

<HighlightGroup>
  {items.map((item) => (
    <HighlightItem key={item.id} asChild active={item.id === selected}>
      <button>{item.label}</button>
    </HighlightItem>
  ))}
</HighlightGroup>
```

## API Reference

### HighlightGroup

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `highlightClassName` | `string` | | Classes for the gliding highlight. |

### HighlightItem

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `active` | `boolean` | `false` | The item the highlight rests on when the pointer leaves. |
| `asChild` | `boolean` | `false` | Merge props onto the child element. |

## Keyboard

The highlight follows keyboard focus when it's visible (`:focus-visible`), so arrow-key navigation inside a group moves it too. It never takes focus itself.

## Accessibility

The highlight element is `aria-hidden` and has `pointer-events: none`. Selection state should still live on your items, for example with `aria-selected` or `aria-current`.

## Motion

The highlight moves with the **snappy** spring and keeps its velocity when you change direction. When the pointer enters a group from outside, it appears in place rather than sliding in from where it last was. A `ResizeObserver` keeps it on the active item through layout changes.

## Notes for AI

- One `HighlightGroup` per list. Nesting groups gives you two highlights.
- Give items a `rounded-*` class that matches `highlightClassName`, so the highlight's corners line up.
